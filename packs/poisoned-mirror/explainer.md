`package.json` in 2.4.1 gained a `postinstall` script, and the registry metadata already said so: `hasInstallScript: true` on 2.4.1 and not on 2.4.0 is the quickest tell that a patch release started running code at install time. npm runs that script on whoever installs the package, with their permissions, which on a CI runner means the pipeline's secrets.

`scripts/setup.js` hides where it goes in three small ways, none of them hard once you look. The host is a base64 string, the path's token is written backwards and reversed at run time, and the last path segment comes from `os.platform()` and `os.arch()`, so the same script fetches something different on each kind of machine. That last part matters for the investigation: a runner on Ubuntu and a developer on a Mac are sent different payloads, and the server only answers a client that looks like Node, so a researcher who fetches it with a browser or `curl` and nothing else sees nothing worth reporting. That is cloaking, the same as in the check-in puzzle.

The second stage (`linux-x64`) collects the environment of the machine and posts it back. On a build runner that is exactly what an attacker wants: tokens, deploy keys and cloud credentials passed in as environment variables. The build id is how the operator tells their victims apart.

What to do about it, when it is real: pin and review dependency updates (a lockfile and `npm ci`, not a floating range), install with `--ignore-scripts` where you can, give build jobs the least access they need and short-lived credentials, and treat any secret a runner exposed to an install step as stolen.
