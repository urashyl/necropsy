Most implants are a polite conversation, *register, ask for work, return results, sleep*, wrapped in a layer or two of packing. Here the packing is a decompress-and-`exec` loader, which is how a lot of Python malware ships: the file on disk is base64 of zlib of the real program, and the real program only exists in memory. The fix for an analyst is always the same. Do not run it. Replace `exec` with `print`, and read what it would have run.

The protocol is small and sound: a fresh 8-byte nonce per message, a keystream made by hashing the key with the nonce and a counter, and an 8-byte HMAC over nonce and ciphertext. It is why you cannot poke at the server and learn anything. The server refuses a reused nonce and a stale timestamp, so a captured beacon cannot simply be replayed, and the capture is only useful as a *test vector* for your own implementation. The key is not in the sample in the clear. It is a constant XORed with a four-byte seed. That is obfuscation, not protection: the implant has to recover the key at run time, so you can too, by calling its own `_k()`.

The craft of this kind of analysis is knowing when not to reimplement. Loading the unpacked source as a module and calling its `_seal` and `_open` is faster and less error-prone than rewriting them, and it is how analysts impersonate implants to learn what an operator's server will say. The operator's mistake is in that reply: after a collection the server sends the implant its *next* key, and here puts the campaign's secret in the same message. Operators routinely leak through the fields they forgot were logged.

For a defender: the beacon is a fixed-interval POST of high-entropy base64url to one rarely seen domain with a `Content-Type` that does not match its body. Those four properties, not any string in the file, are what a network rule can use.
